# 인프라 보완 및 카오스 재측정 — 2026-11-12

## 적용한 보완

- 호스트 SQL: 기존 UFW 허용 목록에도 1433은 없었습니다. 전체 인터페이스 수신만으로 외부 접근 가능하다고 단정할 수 없습니다. IPv4/IPv6 `1433/tcp DENY`를 명시적으로 추가했습니다. 호스트 loopback 접속 성공, Docker 네트워크에서 호스트 1433 접속 차단을 확인했습니다. 재현 스크립트: `deploy/host/restrict-sql.sh`.
- 코드와 stdin의 개별 UTF-8 64KiB 제한은 유지하고 JSON envelope 한도를 브로커·C++ 전달 클라이언트·VM 관리자에서 800,000바이트로 맞췄습니다. JSON 이스케이프 후 크기를 고려합니다.
- FE 노트북은 서버와 같은 UTF-8 전체 셀 JSON 512KiB, 결과 JSON 1MiB 상한을 검사합니다. 가져오기 파일 1MiB와 셀별 64KiB는 서로 다른 제한이며 오류 메시지에 명시합니다.
- VM 설정 조회·변경, 리소스·디스크 변경, Java 의존성 설치, 커널 초기화와 노트북 준비·초기화를 기존 캔버스 WebSocket으로 전환했습니다. 브로커와 C++은 조회에 읽기 권한, 관리에 쓰기+실행 권한을 검사합니다. 실행 대상 노트북/셀 권한은 C++에서 추가 확인합니다.
- C++의 일반 실행 요청은 VM 관리자의 엄격한 요청 필드 정의에 맞춰 불필요한 `action: execute`를 제거했습니다. 관리 작업의 canvasId는 연결된 캔버스 ID로 강제합니다.
- 준비/의존성 작업에 맞춰 timeout을 VM 커널 클라이언트 240초 → 브로커 socket 245초 → broker caller 255초 → FE 260초 순서로 맞췄습니다. 게스트 코드 자체의 실행 제한과는 별개입니다.
- 브로커·Nginx·저장소 브로커 Docker 로그는 각 20MB × 5개로 순환합니다. 7일 지난 빌드 캐시를 정리해 약 3.019GB를 회수했습니다. 앱 데이터·VM 디스크는 삭제하지 않았습니다.

## 남은 전환 범위

캔버스 접속 후 모든 기능의 WebSocket 전환은 완료되지 않았습니다.
파일 업로드/조회, 봇 관리, 참가자 프로필 조회, URL 미리보기, 터미널 티켓 발급,
GitHub 관리/직접 GitHub API 호출 등의 HTTP 경로가 남아 있습니다.
따라서 이 문서는 전체 기능의 완전 WebSocket화를 완료했다고 주장하지 않습니다.
기존 Spring HTTP 실행 API도 호환 경로로 남아 있고 독립적으로 권한을 검사합니다.

## 카오스 방법

실제 운영 이미지와 인증서를 읽기 전용 참조하는 격리 Docker 환경을 사용합니다.
운영 데이터 볼륨과 공개 포트는 연결하지 않습니다. 시험 사용자 이메일 인증 증명은
시험 DB에만 넣고 회원가입/로그인/API/WebSocket 저장 경로는 실제로 수행합니다.
운영 인증 절차를 비활성화하지 않습니다.

Nginx, Spring, 브로커, C++, 저장소 브로커, SQL, ES, Redis 초기 primary를
대상별 1회씩 5초 pause하고 복원합니다. 각 시나리오는 장애 전 5초,
장애 5초, 복원 후 15초 동안 초당 약 4개의 새 사용자 흐름을 시작합니다.
로그인 → 검색 → 접근 토큰 및 WSS 초기 스냅샷 → 저장 ACK와 canonical commit을
각 단계 2초 이내에 마쳐야 성공입니다. 클라이언트 자동 재시도는 없습니다.
별도 무장애 대조군 40건과 최종 스냅샷의 데이터 누락/변형도 검사합니다.
코드 실행, 파일 전송, 브라우저 렌더링은 이 성공률 측정에 포함되지 않습니다.

요청 시작 구간으로 분류하므로 장애 직전 시작한 흐름도 후속 단계가 장애와
겹치면 실패합니다. 이 인위적인 장애 혼합 성공률은 운영 SLA가 아닙니다.
각 1초 구간 성공률은 raw results의 timeline.csv에 기록됩니다.
